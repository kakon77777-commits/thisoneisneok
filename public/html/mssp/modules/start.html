從這裡開始

這個方法要解決什麼

一個專案剛開始的時候，你可以在腦中裝下它的全部。哪個檔案做什麼、改動這裡會影響哪裡、哪些規則不能違反——這些都還在你的工作記憶裡。

問題是這個狀態會結束，而且結束得比大多數人預期的早。當專案同時具備多個角色、多個外部工具、不同風險等級、數十種子任務、可替換的領域能力、版本遷移與長期維護時，「我知道這個系統」這句話會悄悄變成「我知道我上次改過的那部分」。

MSSP（母集與子集範式，Mother-Set and Subset Paradigm）處理的是這個轉折點之後的事。它的主張很短：

不是把程式切碎，而是讓狀態的邊界可以被看見與操作。

這句話裡每個詞都在排除一種常見誤解。「不是把程式切碎」排除了「分成更多資料夾就是模組化」。「邊界可以被看見」排除了「我知道它在哪就夠了」。「可以被操作」排除了「畫在架構圖上就算存在」。

五個集合

MSSP 把一個系統的內容分成五類。它們是角色，不是強制要建的目錄。

FMS（第一主母集） — 這個系統是什麼、為何存在、東西在哪裡。純元資料，零執行邏輯。它服務的對象包含人類，也包含要載入這個系統的 Agent。

SCL（設定契約層） — 什麼可以被改變、由誰改、在什麼風險等級下改。這一層存在的理由是：知識與權限是兩件事。一個模組可以完整描述如何刪除正式資料，同時不擁有刪除的權限。

SMS（第二主母集） — 移除之後，系統就不再是原本那個系統的能力。

TMS（第三主母集） — 按需載入、可替換、可以單獨測試的能力。

DMS（診斷母集） — 人類能看見系統實際做了什麼。

兩個問題決定一切

判斷一個能力屬於 SMS 還是 TMS，只需要問：

  1. 移除它之後，系統的核心任務還能不能閉環？ 不能 → SMS。能 → TMS。
  2. 只載入最小核心、其他 TMS 都不在的情況下，它能不能被測試？ 不能 → 它有隱藏耦合，還不是一個 TMS。

第一個問題最常見的誤答是把「很常用」當成「不可缺少」。一個到處在寫日誌的任務執行器，刪掉日誌模組仍然是任務執行器；刪掉排程就不是了。頻繁使用不等於構成身份。

不確定的時候放 TMS。之後把 TMS 升成 SMS 是一次受控的改動；把 SMS 降成 TMS 意味著每一個依賴者都要重看一遍。

依賴規則

允許：

TMS-A  →  SMS 共享契約  ←  TMS-B

禁止：

TMS-A  →  TMS-B  →  TMS-C  →  TMS-A

兩個 TMS 需要合作時，透過 SMS 持有的介面或事件契約，而不是直接互相 import。一個 TMS 直接引用另一個 TMS，代表其中一個無法單獨載入，於是兩個都不再是真正的子集。

這條規則的檢查方式是機械的：對一個 TMS 模組 grep 有沒有引用任何兄弟 TMS 的路徑。命中一次就是違規，不管它看起來多合理。

什麼時候不該用

這是方法的一部分，不是例外。

規模不足時保持簡單。 一個任務、一個工具、沒有高風險操作、沒有多角色——單一檔案加測試就夠了。在這個規模上建 FMS/SCL/SMS/TMS/DMS，只會讓程式更難讀，換不到任何東西。

過早分層會產生空模組、虛假抽象、導航負擔，以及在還沒有人知道邊界該在哪裡之前就把邊界凍結。最後一項最貴。

真正需要完整 MSSP 的訊號是這些同時出現，不是只出現一項：

  • 超過三種主要角色
  • 超過五個外部工具
  • 超過十個子能力
  • 唯讀與寫入操作並存
  • 存在不可逆的動作
  • 不同任務需要的上下文真的不同
  • 多平台適配
  • 需要長期版本維護
  • 多人或多 Agent 協作
  • 子能力需要獨立測試
  • 一份文件已經無法在幾分鐘內說清楚整個系統

為什麼在 Agent 時代這件事變重要

傳統模組化關心程式碼怎麼拆。當系統的一部分是會讀取上下文並自己決定要做什麼的 Agent 時，多出了一個新的稀缺資源：上下文本身。

上下文有容量、有成本、有注意力競爭、有污染風險。把整個技能系統全量塞進去，等於讓一個只需要其中一項能力的任務讀完所有規則——包括那些會誤導它的規則。

於是可以定義上下文效用密度：

ρq=Itask relevantIloaded\rho_q = \frac{I_{\text{task relevant}}}{I_{\text{loaded}}}ρq​=Iloaded​Itask relevant​​

理想狀況是 ρq→1\rho_q \rightarrow 1ρq​→1 。全量注入會讓 ρq\rho_qρq​ 隨系統規模單調下降。

MSSP 在這裡的作用，是讓「只載入真正需要的子集」從一個願望變成一個結構性質。
