修好真的比較簡單嗎？複雜度轉移與重構悖論

摘要

軟體工程經常把重構、技術債償還、服務拆分與架構清理描述成「降低複雜度」的活動。然而，複雜度並不是一個只能存在於程式碼中的單一標量。當一個大型函式被拆成多個服務、當重複邏輯被集中成共同抽象、當人工流程被自動化、當 legacy adapter 被 framework 取代時，某些局部複雜度確實可能下降，但新的複雜度也可能出現在網路通訊、部署、故障模式、配置、資料一致性、共享基礎設施、組織協調、觀測、驗證與認知負荷中。

2025 年 ICSA 的 architecture technical debt 生命周期研究提供了一個重要實證例子：研究觀察到 ATD repayment 後 FAN-IN 平均增加 57.5%、FAN-OUT 增加 26.7%，顯示償債可以改善某些短期品質，同時使依賴更集中並增加另一種架構複雜度。Microservices 的既有工程經驗也長期指出，較強的模組邊界與獨立部署能力，是以 distribution、eventual consistency 與 operational complexity 等成本交換而來。

本文因此提出「複雜度轉移（Complexity Transfer）」與「重構悖論（Refactoring Paradox）」：一次成功重構可能顯著改善目標區域，卻不必然降低系統的總複雜度；它更可能改變複雜度的位置、型態、集中程度、可見性、承擔者與可自動化程度。

形式上：

Repair⇏Total Complexity Reduction\boxed{ \text{Repair} \nRightarrow \text{Total Complexity Reduction} }Repair⇏Total Complexity Reduction​

更合理的模型為：

Ct+1=T(Ct,R,E)\boxed{ \mathbf{C}_{t+1} = T \left( \mathbf{C}_t, R, E \right) }Ct+1​=T(Ct​,R,E)​

其中 C\mathbf{C}C 是多維複雜度向量， RRR 是重構／架構變換， EEE 是環境，而 TTT 描述複雜度如何被重新分布。

本文建立程式碼、依賴、分布式、操作、資料、配置、認知、組織、驗證與 AI 監督等複雜度維度，並提出「複雜度守恆」不是嚴格物理定律，但「複雜度不應被假定會因抽象或重構而消失」是一項重要工程原則。真正好的重構，不一定讓所有複雜度變少，而是把不可治理、不可觀測、不可替換的複雜度，轉化成更集中、更顯式、更可驗證、更可自動化或更符合責任邊界的複雜度。

本文最後將此命題接回 Dynamic MSSP/FPL：架構治理不能只比較重構前後的 code smell 或 dependency count，而應追蹤「複雜度流」——複雜度從哪裡消失、又在哪裡重新出現，以及新的承擔主體是否真的更適合處理它。

**關鍵詞：**複雜度轉移、重構悖論、architecture technical debt、microservices、operational complexity、leaky abstraction、AI coding、Dynamic MSSP、FPL、軟體結構動力學

1. 「修乾淨了」究竟代表什麼？

軟體重構之後，我們常會說：

這裡乾淨多了。

這句話通常有真實基礎。

例如：

  • 5000 行函式拆成 20 個模組；
  • 重複程式碼被集中；
  • shared database 被拆開；
  • legacy branch 被清除；
  • package cycle 被消除；
  • manual process 被自動化；
  • 巨大 monolith 被拆成服務。

在局部視角：

Clocal(t+1)<Clocal(t)C_{\text{local}}(t+1) < C_{\text{local}}(t)Clocal​(t+1)<Clocal​(t)

完全可能。

問題是：

這是否意味整個系統真的變簡單？

答案不是必然。

因為「局部簡單」可以透過把責任推到其他地方取得。

2. 2025 ICSA：償還技術債後，依賴反而更集中

2025 年 ICSA 的研究 Tracing the Lifecycle of Architecture Technical Debt in Software Systems: A Dependency Approach 對 architecture technical debt 的生命周期與依賴變化進行分析。

其中最值得本文注意的結果是：

  • ATD repayment 後 FAN-IN 平均增加 57.5%；
  • FAN-OUT 平均增加 26.7%。

研究者指出，這代表償還 architecture technical debt 可以改善短期品質，同時使依賴向某些位置集中，增加另一種架構複雜度。

這個結果非常重要，因為它反駁了一個過度簡化的直覺：

Debt Repaid⇒Complexity Lower\text{Debt Repaid} \Rightarrow \text{Complexity Lower}Debt Repaid⇒Complexity Lower

更可能是：

Debt Repaid⇒Dependency Topology Changed\text{Debt Repaid} \Rightarrow \text{Dependency Topology Changed}Debt Repaid⇒Dependency Topology Changed

甚至：

Local Disorder Reduced→Central Dependency Increased\text{Local Disorder Reduced} \rightarrow \text{Central Dependency Increased}Local Disorder Reduced→Central Dependency Increased

也就是：

修復不是把複雜度消掉，而可能是把分散複雜度重新集中。

3. 重構悖論

本文因此定義：

重構悖論

Refactoring Paradox

一次重構可以成功改善其直接目標，同時使系統在其他維度產生新的複雜度或負擔。

形式上：

ΔCi<0\Delta C_i < 0ΔCi​<0

不代表：

∑jΔCj<0\sum_j \Delta C_j < 0j∑​ΔCj​<0

其中 CiC_iCi​ 是某一類複雜度。

例如：

Ccode↓C_{\text{code}}\downarrowCcode​↓

但：

Coperations↑C_{\text{operations}}\uparrowCoperations​↑

仍然可能。

這不是「重構失敗」。

相反地，它可能是完全合理的工程交換。

真正錯誤的是：

只測量下降的那一維，然後宣稱複雜度消失了。

6. 第二種轉移：Monolith → Distribution

Microservices 是複雜度轉移最清楚的案例之一。

Martin Fowler 對 microservice trade-offs 的整理指出，其優點包括：

  • stronger module boundaries；
  • independent deployment；
  • technology diversity。

但同時帶來：

  • distribution complexity；
  • eventual consistency；
  • operational complexity。

Microsoft 的 microservice architecture 指南同樣指出，分散應用增加：

  • service communication；
  • testing；
  • exception handling；
  • latency；
  • deployment；
  • distributed transaction；

等複雜度。

因此：

Cmodule-boundary↓C_{\text{module-boundary}}\downarrowCmodule-boundary​↓

可能同時：

Cdistribution↑C_{\text{distribution}}\uparrowCdistribution​↑ Coperations↑C_{\text{operations}}\uparrowCoperations​↑ Cstate consistency↑C_{\text{state consistency}}\uparrowCstate consistency​↑

所以 microservices 不是：

Complex System→Many Simple Systems\text{Complex System} \rightarrow \text{Many Simple Systems}Complex System→Many Simple Systems

而更接近：

In-process Complexity→Inter-service Complexity\text{In-process Complexity} \rightarrow \text{Inter-service Complexity}In-process Complexity→Inter-service Complexity

9. 抽象的真正價值：重新分配認知，而不是消滅世界

這並不降低 abstraction 的價值。

恰恰相反。

好的 abstraction 很重要，因為它讓大部分使用者在大部分時間不需要處理底層細節。

因此它降低：

Ch(common path)C_h^{(\text{common path})}Ch(common path)​

即日常認知複雜度。

但在 failure／edge case：

Ch(exception path)C_h^{(\text{exception path})}Ch(exception path)​

可能重新上升。

所以抽象的真正價值不是：

底層不複雜了。

而是：

把需要處理複雜度的人數、頻率與情境縮小。

這是非常重要的複雜度治理思想。

17. 不應叫「複雜度守恆定律」

這裡必須保持理論嚴謹。

直覺上很容易說：

複雜度不會消失，只會轉移。

但這不能當成嚴格定律。

因為優秀演算法、正確抽象、需求刪除、資料模型改善，確實可以真正降低總複雜度。

例如：

O(n2)→O(nlog⁡n)O(n^2) \rightarrow O(n\log n)O(n2)→O(nlogn)

可能是實質改善。

刪除不再需要的 feature，也可能真正：

Ctotal↓C_{\text{total}}\downarrowCtotal​↓

所以本文不提出：

Complexity Conservation Law

而提出較弱、可防止誤判的原則：

Complexity Non-Disappearance Assumption

即：

在重構或抽象後，不應預設被局部消除的複雜度已從整個系統消失；必須檢查它是否被刪除、壓縮、隱藏、集中或轉移。

20. 好的複雜度轉移

複雜度轉移不應被污名化。

好的轉移通常具有以下特徵：

20.1 從不可見 → 可見

Cimplicit→CexplicitC_{\text{implicit}} \rightarrow C_{\text{explicit}}Cimplicit​→Cexplicit​

20.2 從人工記憶 → 可驗證規格

Ctacit→Cmachine-checkableC_{\text{tacit}} \rightarrow C_{\text{machine-checkable}}Ctacit​→Cmachine-checkable​

20.3 從到處重複 → 集中平台

Cduplicated→CcentralizedC_{\text{duplicated}} \rightarrow C_{\text{centralized}}Cduplicated​→Ccentralized​

20.4 從難自動化 → 易自動化

Cmanual→CautomatableC_{\text{manual}} \rightarrow C_{\text{automatable}}Cmanual​→Cautomatable​

20.5 從錯誤 owner → 正確 owner

Cmisowned→Cproperly ownedC_{\text{misowned}} \rightarrow C_{\text{properly owned}}Cmisowned​→Cproperly owned​

所以真正目標不是：

複雜度零。

而是：

複雜度出現在最適合承擔它的位置。

21. 壞的複雜度轉移

反過來，壞轉移可能是：

21.1 從顯式 → 隱式

clear business rules
→ magical framework behavior

21.2 從局部 → 全局

local helper
→ shared singleton

21.3 從技術 → 人工

automated validation removed
→ operator must remember

21.4 從 code → configuration without validation

if/else
→ huge YAML

21.5 從開發 → 使用者

system cannot resolve ambiguity
→ user manually cleans everything

此時局部工程數字可能改善，

但：

Ceffective system↑C_{\text{effective system}}\uparrowCeffective system​↑

22. 重構評估需要「前後複雜度向量」

因此一次重要重構前，可以記錄：

Cbefore\mathbf{C}_{\text{before}}Cbefore​

重構後：

Cafter\mathbf{C}_{\text{after}}Cafter​

再計算概念上的：

ΔC=Cafter−Cbefore\Delta\mathbf{C} = \mathbf{C}_{\text{after}} - \mathbf{C}_{\text{before}}ΔC=Cafter​−Cbefore​

例如：

complexity_delta:
  code: -0.40
  dependency: +0.15
  operations: +0.20
  data: +0.05
  cognitive: -0.30
  verification: +0.10

這不是要假裝數字可以精確比較不同維度。

而是建立：

多維變化帳本。

23. 再加入「可治理性」

複雜度本身還不是唯一重要變量。

定義：

G(C)=Governability of ComplexityG(C) = \text{Governability of Complexity}G(C)=Governability of Complexity

考慮：

  • observability；
  • ownership；
  • testability；
  • determinism；
  • documentation；
  • tooling；
  • reversibility；
  • automation。

則一個重構即使：

CtotalC_{\text{total}}Ctotal​

沒有明顯下降，

但：

G(C)↑G(C)\uparrowG(C)↑

仍然可能是非常成功的架構改善。

例如：

10 種 undocumented human exceptions

轉成：

1 個複雜但有 schema、tests、owner 的 policy engine

總語義不一定少很多。

但治理能力提高巨大。

24. 重構效益的新模型

因此，重構價值不應只寫成：

VR=−ΔCV_R = -\Delta CVR​=−ΔC

而可以概念化為：

VR=αΔG+βΔO+γΔRv+δΔA−λΔCharmfulV_R = \alpha \Delta G + \beta \Delta O + \gamma \Delta R_v + \delta \Delta A - \lambda \Delta C_{\text{harmful}}VR​=αΔG+βΔO+γΔRv​+δΔA−λΔCharmful​

其中：

  • ΔG\Delta GΔG ：governability 改善；
  • ΔO\Delta OΔO ：observability 改善；
  • ΔRv\Delta R_vΔRv​ ：reversibility 改善；
  • ΔA\Delta AΔA ：automation potential；
  • ΔCharmful\Delta C_{\text{harmful}}ΔCharmful​ ：有害複雜度變化。

意思是：

好的架構改善未必把系統變得「簡單」，但應把它變得更可理解、更可驗證、更可逆、更能被正確主體治理。

25. Dynamic MSSP：從 Architecture Diff 升級成 Complexity Flow

因此未來 FPL/MSSP 的重構分析不應只有：

before graph
vs
after graph

還應記錄：

transformation:
  id: extract-payment-core

  removed:
    - duplicated_payment_rules

  introduced:
    - payment_core_service
    - service_api
    - retry_policy
    - tracing
    - deployment_unit

  complexity_flow:
    code_to_dependency: medium
    code_to_operations: high
    local_to_platform: medium

  benefits:
    module_boundary: high
    testability: high
    independent_deployment: medium

  new_risks:
    network_failure: medium
    centrality: high

  evidence:
    - dependency_graph
    - runtime_trace
    - deployment_metrics

這樣 AI 才不會只看到：

cycle 消失了，好耶。

而是繼續問：

cycle 消失後，複雜度跑去哪裡？

26. AI Agent 可以做複雜度流偵測

AI 特別適合分析：

Cbefore→Cafter\mathbf{C}_{\text{before}} \rightarrow \mathbf{C}_{\text{after}}Cbefore​→Cafter​

因為證據可能跨越：

  • code diff；
  • dependency graph；
  • CI；
  • infrastructure；
  • config；
  • runtime；
  • ticket；
  • incident；
  • human workflow。

可以讓 Agent 提出：

Hypothesis:
The refactor reduced local duplication,
but increased central dependency and
introduced two new operational failure modes.

並附：

  • evidence；
  • confidence；
  • counterevidence。

這仍然是：

AI Hypothesis≠Truth\text{AI Hypothesis} \neq \text{Truth}AI Hypothesis=Truth

但比單一 lint metric 更接近架構現實。

27. AI 本身也是複雜度轉移器

更有趣的是：

Dynamic MSSP 本身會把：

Chuman architecture reviewC_{\text{human architecture review}}Chuman architecture review​

部分轉移到：

CAI inference+Cevidence pipeline+CverificationC_{\text{AI inference}} + C_{\text{evidence pipeline}} + C_{\text{verification}}CAI inference​+Cevidence pipeline​+Cverification​

這不是問題。

只要：

G(Cnew)>G(Cold)G(C_{\text{new}}) > G(C_{\text{old}})G(Cnew​)>G(Cold​)

就可能值得。

也就是：

AI 的真正價值不必是「讓複雜度消失」。

它可以是：

把人類難以持續處理的複雜度，轉成機器可以持續觀測、搜尋、比對與預警的形式。

28. 命題 7：複雜度轉移命題

本文提出系列第七命題。

複雜度轉移命題

對軟體系統 SSS 施加架構變換或重構 RRR ：

St→RSt+1S_t \overset{R}{\rightarrow} S_{t+1}St​→RSt+1​

即使某一複雜度維度下降：

Ci(St+1)<Ci(St)C_i(S_{t+1}) < C_i(S_t)Ci​(St+1​)<Ci​(St​)

也不能推出：

Ctotal(St+1)<Ctotal(St)C_{\text{total}}(S_{t+1}) < C_{\text{total}}(S_t)Ctotal​(St+1​)<Ctotal​(St​)

因為可能存在：

∃j:Cj(St+1)>Cj(St)\exists j: C_j(S_{t+1}) > C_j(S_t)∃j:Cj​(St+1​)>Cj​(St​)

因此：

Repair⇏Total Complexity Reduction\boxed{ \text{Repair} \nRightarrow \text{Total Complexity Reduction} }Repair⇏Total Complexity Reduction​

而更合理的分析對象是：

ΔC+FC+ΔG\boxed{ \Delta\mathbf{C} + \mathbf{F}_C + \Delta G }ΔC+FC​+ΔG​

即：

  • 複雜度向量變化；
  • 複雜度流；
  • 可治理性變化。

29. 重構悖論的強版本

由此可以得到：

最成功的重構，有時不是讓系統擁有更少複雜度，而是讓複雜度終於出現在正確的地方。

例如：

Hidden Human Knowledge→Explicit Rules\text{Hidden Human Knowledge} \rightarrow \text{Explicit Rules}Hidden Human Knowledge→Explicit Rules Duplicated Logic→Central Service\text{Duplicated Logic} \rightarrow \text{Central Service}Duplicated Logic→Central Service Implicit Deployment Ritual→CI/CD Pipeline\text{Implicit Deployment Ritual} \rightarrow \text{CI/CD Pipeline}Implicit Deployment Ritual→CI/CD Pipeline Local Failure Guessing→Observability Platform\text{Local Failure Guessing} \rightarrow \text{Observability Platform}Local Failure Guessing→Observability Platform

這些改造甚至可能增加：

  • code；
  • config；
  • infrastructure；

但整體：

G(C)G(C)G(C)

大幅提高。

所以：

More Artifacts⇏Worse Architecture\boxed{ \text{More Artifacts} \not\Rightarrow \text{Worse Architecture} }More Artifacts⇒Worse Architecture​

同樣：

Less Code⇏Less System Complexity\boxed{ \text{Less Code} \not\Rightarrow \text{Less System Complexity} }Less Code⇒Less System Complexity​

30. 結論：複雜度最重要的不是多少，而是在哪裡、誰承擔、能不能治理

本文從一個常見工程直覺開始：

「我們把它重構了，所以它更簡單。」

這句話可能正確。

但必須先回答：

哪一部分變簡單？

因為軟體複雜度可以在：

  • code；
  • dependency；
  • network；
  • operations；
  • data；
  • configuration；
  • cognition；
  • organization；
  • verification；
  • AI supervision；

之間轉移。

因此：

Local Simplicity⇏Global Simplicity\boxed{ \text{Local Simplicity} \nRightarrow \text{Global Simplicity} }Local Simplicity⇏Global Simplicity​

而：

Abstraction⇏Complexity Elimination\boxed{ \text{Abstraction} \nRightarrow \text{Complexity Elimination} }Abstraction⇏Complexity Elimination​

同樣不能直接成立。

但本文也不主張「複雜度永遠守恆」。

真正的工程原則是：

不要假設複雜度已經消失。先追蹤它。

因此一次架構變換後應問：

  1. 哪種複雜度真的被消除了？
  2. 哪種只是被隱藏？
  3. 哪種被集中？
  4. 哪種被轉移？
  5. 新位置是否更容易觀測？
  6. 是否有明確 owner？
  7. 是否更容易驗證與自動化？
  8. 是否增加新的單點或組織依賴？

最終，好的架構不是：

C→0C\rightarrow0C→0

而更接近：

Complexity→Right Place+Right Owner+Right Evidence+Right Tooling\boxed{ \text{Complexity} \rightarrow \text{Right Place} + \text{Right Owner} + \text{Right Evidence} + \text{Right Tooling} }Complexity→Right Place+Right Owner+Right Evidence+Right Tooling​

這也把系列推向下一個問題。

如果軟體只要持續成功，就會持續改變；如果每次改變又都可能重新分配複雜度，那麼：

成功軟體為什麼幾乎必然越活越複雜？
