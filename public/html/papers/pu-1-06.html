Failure Is Also Program: Verification, Observability, Recovery, and Long-Term Maintenance

摘要

第 1 冊前五篇依序將程式定義為可執行問題模型，建立問題世界、資料—狀態—事件—行動四元動力、責任模組與契約，以及可視化外部結構記憶。本篇作為第 1 冊封頂篇，集中處理最容易被錯誤地視為「例外」或「開發後期工作」的部分：失敗、驗證、可觀測、恢復與長期維護。

本文提出：

Failure Handling≠Peripheral Exception Code\boxed{ \text{Failure Handling} \neq \text{Peripheral Exception Code} }Failure Handling=Peripheral Exception Code​

以及更核心的命題：

Failure Is Also Program\boxed{ \text{Failure Is Also Program} }Failure Is Also Program​

如果程式是一個可執行問題模型，那麼失敗就不是偏離程式的外部事件，而是問題世界中可預期、可分類、可觀測、可恢復或不可恢復的正式狀態與路徑。只描述成功流程的程式，並沒有描述完整世界。

本文提出系統失敗結構：

FP=⟨D,C,S,I,P,O,R,E,L,M⟩\boxed{ \mathcal F_P = \left\langle D, C, S, I, P, O, R, E, L, M \right\rangle }FP​=⟨D,C,S,I,P,O,R,E,L,M⟩​

其中：

  • DDD ：Detection，失敗如何被發現；
  • CCC ：Classification，失敗如何分類；
  • SSS ：Scope，影響範圍；
  • III ：Impact，對主體、狀態與外部世界的影響；
  • PPP ：Propagation，失敗如何傳播；
  • OOO ：Observability，系統如何呈現真實狀態；
  • RRR ：Recovery，如何重試、回復、降級、補償或重建；
  • EEE ：Evidence，完成與失敗的證據；
  • LLL ：Learning，事故如何轉化為結構改進；
  • MMM ：Maintenance，系統如何跨版本與時間持續可理解。

本文區分：

  • 錯誤 Error：系統內部的錯誤條件、違反假設或非法狀態；
  • 失敗 Failure：系統無法履行某項契約、責任或世界效果；
  • 事故 Incident：失敗已經影響使用者、受影響主體、制度或物理世界；
  • 災難 Catastrophe：失敗超過既有恢復能力並造成大範圍或不可逆影響。

本文主張：

Error⇏Failure⇏Incident⇏Catastrophe\boxed{ Error \not\Rightarrow Failure \not\Rightarrow Incident \not\Rightarrow Catastrophe }Error⇒Failure⇒Incident⇒Catastrophe​

錯誤若被局部吸收，不必成為外部失敗；失敗若被隔離與恢復，不必成為事故；事故若具有邊界、回復與補救，不必升級為災難。系統韌性不等於沒有錯誤，而是能阻止錯誤沿責任與依賴鏈無限制擴散。

本文建立「驗證階梯」：

  1. 結構驗證：格式、型別與 schema；
  2. 語意驗證：資料與操作是否具有合法問題世界意義；
  3. 狀態驗證：前置條件與不變量是否成立；
  4. 權限驗證：主體是否具有合法行動權；
  5. 效果驗證：權威狀態是否真正改變；
  6. 外部驗證：數位或物理世界效果是否有證據；
  7. 目的驗證：受影響主體是否接受結果，原始目的是否仍成立。

因此：

TestPass⁡⇏WorldCorrect⁡\boxed{ \operatorname{TestPass} \not\Rightarrow \operatorname{WorldCorrect} }TestPass⇒WorldCorrect​

測試通過只能證明已測條件下的某些性質，不能自動證明問題世界完整、外部效果成立或目的合理。

本文也將可觀測性定義為：

系統能否僅憑外部可取得的證據，重建其內部狀態、重要事件、責任、因果、影響與恢復位置的能力。

形式上：

OP=⟨State,Event,Trace,Metric,Log,Evidence,Context,Ownership⟩\boxed{ \mathcal O_P = \left\langle State, Event, Trace, Metric, Log, Evidence, Context, Ownership \right\rangle }OP​=⟨State,Event,Trace,Metric,Log,Evidence,Context,Ownership⟩​

可觀測性不是「有日誌」或「有監控儀表板」。若無法回答：

  • 現在世界處於什麼狀態；
  • 哪個事件造成變化；
  • 誰執行；
  • 哪條規則與契約生效；
  • 影響哪些主體；
  • 是否部分成功；
  • 誰負責回復；

則系統仍不可觀測。

本文提出恢復五分法：

  1. Retry：在相同行動身份下重試，不重複世界效果；
  2. Rollback：回到先前數位狀態；
  3. Compensation：以新行動抵銷已發生效果；
  4. Degradation：降低能力以保存核心責任；
  5. Reconstruction：由事件、快照、備份與外部證據重建世界。

本文特別強調：

Rollback⁡D⇏Rollback⁡W\boxed{ \operatorname{Rollback}_D \not\Rightarrow \operatorname{Rollback}_W }RollbackD​⇒RollbackW​​

數位狀態可以回滾，但通知、付款、物理操作、公開資訊與人類決策可能已經發生。成熟恢復設計必須區分可撤銷、可補償、只能說明、以及完全不可逆的效果。

本文進一步提出「維護不是修補，而是持續重新理解」。長期維護包含：

  • 規則演化；
  • schema 與契約版本；
  • 相依更新；
  • Runtime 漂移；
  • 權限變化；
  • 視圖更新；
  • 知識交接；
  • 技術債與限制性債務；
  • 事故學習；
  • 退役與資料遷移。

本文將維護成熟度表示為：

Maintainability=Comprehensibility+Traceability+Reversibility+Replaceability+HistoricalMemory\boxed{ Maintainability = Comprehensibility + Traceability + Reversibility + Replaceability + Historical Memory }Maintainability=Comprehensibility+Traceability+Reversibility+Replaceability+HistoricalMemory​

若系統只能由原作者修改、無法知道變更影響、無法局部回復、不能替換相依、沒有歷史決策記憶，即使目前可運作，也不具有長期可維護性。

本文使用訂單付款、網站部署、AI Agent、醫療系統、研究平台與多團隊服務等案例，分析失敗如何成為正式狀態。本文最後提出可證偽研究綱領，包括失敗檢出延遲、錯誤到事故轉化率、可觀測性覆蓋、恢復成功率、補償完整性、事故定位時間、責任辨識、變更失敗率、知識單點、視圖漂移、退役殘留與事故學習閉環。

本文作為第 1 冊結論，將系統性程式設計收束為：

Problem World→Dynamic State→Responsibility→Contract→Shared Understanding→Failure and Recovery\boxed{ \text{Problem World} \rightarrow \text{Dynamic State} \rightarrow \text{Responsibility} \rightarrow \text{Contract} \rightarrow \text{Shared Understanding} \rightarrow \text{Failure and Recovery} }Problem World→Dynamic State→Responsibility→Contract→Shared Understanding→Failure and Recovery​

Abstract

This paper concludes Volume 1 by arguing that failure handling is not peripheral exception code. Failure is part of the program.

A system failure structure is modeled as:

FP=⟨D,C,S,I,P,O,R,E,L,M⟩\mathcal F_P = \left\langle D, C, S, I, P, O, R, E, L, M \right\rangleFP​=⟨D,C,S,I,P,O,R,E,L,M⟩

The paper distinguishes errors, failures, incidents, and catastrophes; develops a seven-level verification ladder; defines observability as the ability to reconstruct state, events, responsibility, causality, impact, and recovery position from external evidence; and distinguishes retry, rollback, compensation, degradation, and reconstruction.

Maintainability is defined as the combination of comprehensibility, traceability, reversibility, replaceability, and historical memory.

Keywords: failure engineering, verification, observability, recovery, maintenance, resilience

一、問題的提出：只畫成功流程的程式，只描述了一半世界

許多設計文件呈現：

輸入
→ 驗證
→ 執行
→ 成功

失敗則被濃縮為：

catch error
return 500

但真實系統可能出現：

  • 輸入有效但世界狀態已改變；
  • 行動已部分執行；
  • 外部服務成功但回覆遺失；
  • 系統內部成功但物理效果未發生；
  • 重試造成重複付款；
  • 回滾後通知已被使用者讀取；
  • 補償失敗；
  • 沒有人知道誰負責結案。

所以失敗不是成功流程之外的雜訊。

失敗本身具有：

  • 狀態；
  • 時間；
  • 主體；
  • 責任；
  • 影響；
  • 證據；
  • 恢復路徑。

三、錯誤、失敗、事故與災難

3.1 錯誤 Error

錯誤是內部條件偏離預期，例如：

  • 型別不符；
  • 不變量失敗；
  • 相依回覆無效；
  • 程式缺陷；
  • 假設失效。

錯誤可以被局部捕捉與吸收。

3.2 失敗 Failure

失敗是系統未能履行某項契約或責任。

例如：

  • 無法完成付款授權；
  • 無法保存資料；
  • 無法在期限內發布；
  • 無法提供承諾的查詢新鮮度。

3.3 事故 Incident

當失敗已影響：

  • 使用者；
  • 受影響者；
  • 制度；
  • 外部服務；
  • 物理世界；

便成為事故。

3.4 災難 Catastrophe

災難是影響超出既有隔離、回復與補救能力，並可能造成廣泛或不可逆後果。

3.5 升級鏈

Error⇏Failure⇏Incident⇏Catastrophe\boxed{ Error \not\Rightarrow Failure \not\Rightarrow Incident \not\Rightarrow Catastrophe }Error⇒Failure⇒Incident⇒Catastrophe​

系統韌性的目的，是在每一層阻止不必要升級。

四、失敗應是一等狀態

4.1 不是所有失敗都應轉成例外

可預期世界狀態，例如：

  • 付款被拒；
  • 使用者取消；
  • 資料等待人工審核；
  • 外部結果未知；
  • 庫存不足；

不應全部被當成技術例外。

4.2 失敗狀態

系統應正式表示：

rejected
timed-out
partially-complete
outcome-unknown
compensation-pending
degraded
human-intervention-required
irrecoverable

4.3 失敗身份

重要失敗需要：

  • failure_id；
  • affected_entity；
  • originating_action；
  • related_events；
  • current_owner；
  • impact；
  • recovery_state。

4.4 二元結果不足

只使用 success／failure 會壓平：

  • 是否已產生部分效果；
  • 是否可安全重試；
  • 是否需要補償；
  • 是否等待外部證據；
  • 是否已影響他人。

五、驗證階梯

本文提出七層驗證。

5.1 結構驗證

檢查：

  • 型別；
  • schema；
  • 必填欄位；
  • 編碼；
  • 範圍。

結構正確不代表語意正確。

5.2 語意驗證

檢查資料與操作是否具有合法問題世界意義。

例如金額欄位格式正確，但使用錯誤幣別或錯誤訂單，仍屬語意錯誤。

5.3 狀態驗證

檢查：

  • 前置條件；
  • 當前版本；
  • 不變量；
  • 是否已終止；
  • 是否處於爭議。

5.4 權限驗證

確認主體是否能在此情境、時間與作用域下執行。

5.5 效果驗證

確認權威狀態真正改變，且未破壞其他不變量。

5.6 外部驗證

確認外部數位或物理效果是否有足夠證據。

5.7 目的驗證

確認原始目的仍成立，且結果被必要主體接受。

5.8 驗證鏈

六、測試不等於完整驗證

6.1 單元測試

驗證局部函式與模組行為。

6.2 整合測試

驗證契約、資料、時間與相依互動。

6.3 系統測試

驗證整體工作流與權威狀態。

6.4 外部效果測試

驗證真實部署、第三方與物理世界效果。

6.5 人類接受

驗證使用者、領域專家與受影響者是否接受。

6.6 核心命題

TestPass⁡⇏WorldCorrect⁡\boxed{ \operatorname{TestPass} \not\Rightarrow \operatorname{WorldCorrect} }TestPass⇒WorldCorrect​

測試通過只代表已明示測試在其假設下通過。

6.7 測試盲區

未測內容可能包括：

  • 未知主體；
  • 規則衝突；
  • 長時延遲；
  • 真實流量；
  • 權限組合；
  • 歷史資料；
  • 外部不可逆效果。

八、可觀測性的正式定義

本文定義：

可觀測性是系統能否僅憑可取得的外部證據，重建其內部狀態、重要事件、責任、因果、影響與恢復位置的能力。

形式上：

OP=⟨State,Event,Trace,Metric,Log,Evidence,Context,Ownership⟩\boxed{ \mathcal O_P = \left\langle State, Event, Trace, Metric, Log, Evidence, Context, Ownership \right\rangle }OP​=⟨State,Event,Trace,Metric,Log,Evidence,Context,Ownership⟩​

8.1 State

現在問題世界與工作流處於何種狀態。

8.2 Event

哪些重要事情已經發生。

8.3 Trace

一次意圖如何跨模組、契約與相依傳播。

8.4 Metric

系統整體趨勢、容量與異常。

8.5 Log

局部處理細節與除錯資料。

8.6 Evidence

能證明世界效果與責任的資料。

8.7 Context

版本、環境、主體、規則與時間。

8.8 Ownership

誰應查看、處理、恢復與結案。

九、日誌、指標、追蹤與事件的區分

9.1 日誌

適合記錄局部處理細節，但可能：

  • 重複；
  • 無語意；
  • 缺少身份；
  • 難以關聯；
  • 被大量噪音淹沒。

9.2 指標

適合觀察趨勢：

  • 錯誤率；
  • 延遲；
  • 吞吐；
  • 資源；
  • 佇列。

但指標通常無法還原單一世界事件。

9.3 分散式追蹤

連接一次行動跨模組的處理路徑。

但追蹤拓撲不自動知道領域責任。

9.4 領域事件

保存具有問題世界意義的已發生事實。

9.5 證據

證據回答「為何相信完成或失敗」。

成熟可觀測性需把四者連接，而不是只大量收集資料。

十、可觀測性必須回答的問題

一個可觀測系統至少應回答：

  1. 哪個主體提出了哪個行動？
  2. 行動依據哪個狀態版本？
  3. 哪個模組作出決策？
  4. 使用哪條規則與契約版本？
  5. 產生哪些事件？

十二、恢復五分法

本文區分：

Recovery=Retry∪Rollback∪Compensation∪Degradation∪Reconstruction\boxed{ Recovery = Retry \cup Rollback \cup Compensation \cup Degradation \cup Reconstruction }Recovery=Retry∪Rollback∪Compensation∪Degradation∪Reconstruction​

12.1 Retry

在相同行動身份下重新嘗試。

條件：

  • 行動仍有效；
  • 前置狀態未失效；
  • 操作具冪等；
  • 結果不是未知；
  • 重試不擴大傷害。

12.2 Rollback

回到先前數位狀態。

適合：

  • 尚未產生外部不可逆效果；
  • 狀態快照可靠；
  • 後續相依可同步回復。

12.3 Compensation

以新行動抵銷已發生效果，例如：

  • 退款；
  • 釋放庫存；
  • 撤回發布；
  • 恢復權限；
  • 修正公告。

12.4 Degradation

保留核心責任，暫時降低能力：

  • 唯讀模式；
  • 關閉推薦；
  • 暫停自動化；
  • 改由人工審核；
  • 使用較舊但穩定版本。

12.5 Reconstruction

由：

  • 事件歷史；
  • 快照；
  • 備份；
  • 外部證據；
  • 人工核對；

重建狀態。

十九、事故學習不等於責任消失

19.1 無責備不等於無責任

事故分析應避免把複雜系統問題簡化為個人疏忽，但仍需保留：

  • 契約；
  • 權限；
  • 審核；
  • 失敗所有權；
  • 補救責任。

19.2 根因不是單一原因

事故常由：

  • 世界模型缺失；
  • 隱含假設；
  • 邊界錯置；
  • 契約模糊；
  • 觀測不足；
  • 壓力與時間；
  • 組織誘因；

共同形成。

19.3 學習產物

事故後應更新：

  • 問題世界；
  • 規則；
  • 不變量；
  • 契約；
  • 測試；
  • 可觀測；
  • 回復程序；
  • 視圖；
  • 教學與值班知識。

19.4 關閉條件

事故不應只在服務恢復後關閉。

還需確認：

  • 世界影響已被理解；
  • 受影響者已獲通知或補救；
  • 殘留風險有責任者；
  • 結構改進已追蹤。

二十、長期維護的正式結構

本文提出：

21.1 修補式維護

只處理：

  • bug；
  • 相依升級；
  • 效能；
  • 小功能。

21.2 結構性維護

還需要重新檢查：

  • 問題世界是否改變；
  • 實體與關係是否仍正確；
  • 規則是否仍正當；
  • 模組邊界是否漂移；
  • 契約是否仍可理解；
  • 視圖是否仍準確；
  • 失敗處理是否仍有效。

21.3 規範性維護

當制度、權利與受影響主體改變，系統不能只更新程式碼。

21.4 物理維護

硬體、網路、能源、憑證與外部服務都會老化或終止。

二十二、技術債、語意債與責任債

22.1 技術債

為短期交付累積的實作成本。

22.2 語意債

程式碼仍能運作，但：

  • 權威來源不明；
  • 規則散落；
  • 歷史無法重建。

22.3 責任債

系統具有重要工作，但沒有清楚：

  • 狀態所有者；
  • 失敗所有者；
  • 使用者結案所有者；
  • 規則修改者。

22.4 觀測債

系統新增能力與相依，卻沒有同步增加足夠證據與追蹤。

22.5 恢復債

備份、補償與回復方法存在於文件或想像中，但未被演練。

三十二、主要失敗模式

  1. 成功流程中心論： 只設計正常路徑，把失敗交給通用例外。
  2. 所有失敗皆例外： 將拒絕、等待、未知與部分成功當成技術錯誤。
  3. 例外即處理： 捕捉錯誤後只記錄或轉換狀態碼，沒有恢復責任。
  4. 錯誤等於事故： 局部可吸收錯誤被過度升級。
  5. 事故等於錯誤： 已影響使用者的事件仍只以內部 bug 處理。
  6. 驗證停在格式： schema 正確便宣稱世界語意正確。
  7. 測試通過即世界正確： 忽略未知條件、外部效果與目的接受。
  8. 只有案例測試： 沒有不變量、性質、狀態空間與歷史資料驗證。
  9. 有日誌即可觀測： 無法從大量文字重建狀態、因果與責任。
  10. 指標無世界語意： 只知道錯誤率升高，不知道影響何種主體與責任。
  11. 追蹤無契約： 看得見呼叫鏈，卻不知道每一步成功代表什麼。
  12. 告警無所有者： 訊號產生後無明確處理、升級與結案責任。
  13. 重試一切： 權限拒絕、永久錯誤與結果未知被盲目重試。
  14. 回滾萬能論： 忽略外部效果與人類認知已經發生。
  15. 補償等於抵銷全部： 不記錄時間、費用、信任與資訊殘差。
  16. 降級即關閉安全： 為保持可用而取消驗證、權限或稽核。
  17. 備份等於可恢復： 從未演練，缺少版本、金鑰、Runtime 與程序。
  18. 服務恢復即事故結案： 未處理使用者影響、補償與殘留風險。
  19. 根因單一化： 把事故歸因於最後一個操作或個人。
  20. 無責備等於無責任： 為避免個人責難而抹除決策與補救責任。
  21. 事後文件化： 事故知識只留在報告，未更新規則、測試、契約與視圖。
  22. 維護即修 bug： 不重新檢查世界、責任、契約與權限。
  23. 程式碼版本唯一化： 忽略資料、規則、事件、Runtime 與視圖版本。
  24. 語意債隱形： 名稱與真實世界意義已分離，仍以能運作為由拖延。
  25. 責任債隱形： 重要流程沒有失敗所有者與使用者結案所有者。
  26. 恢復債隱形： 回復程序未演練，卻在文件中被視為可用。
  27. 遷移無狀態： 資料轉換被當成一次腳本，沒有檢查點與補償。
  28. 退役即關機： 舊權限、API、資料、文件與外部依賴持續殘留。
  29. 知識英雄化： 只有原作者知道如何診斷與恢復。
  30. AI 自動恢復越權： Agent 在未知結果或不可逆狀態下自行重試、回滾或補償。

三十七、結論：可靠不是不失敗，而是不讓世界在失敗中失去方向

任何真正長期運作的系統都會遇到：

  • 錯誤；
  • 相依失效；
  • 資料漂移；
  • 規則變更；
  • 人類誤解；
  • 未知事件；
  • 資源不足；
  • 攻擊；
  • 組織調整；
  • 技術退役。

所以，要求系統永不失敗並不現實。

但這不代表只能接受混亂。

系統仍可以被設計成：

  • 失敗可被快速發現；
  • 影響範圍可被限制；
  • 當前狀態可被重建；
  • 責任可被辨認；
  • 外部效果可被驗證；
  • 結果未知不被偽裝成成功；
  • 可逆效果能回復；
  • 不可逆效果能補償與說明；
  • 核心責任能降級保存；
  • 事故能轉化為下一版本的結構改善。
